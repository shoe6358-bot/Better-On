# Architecture and implementation plan

## Foundation decision

Use the stable KDE desktop variant of Bazzite as the upstream base, packaged as a bootc-compatible OCI image with the Universal Blue image-template pattern. Bazzite supplies the supported Fedora Atomic base, KDE Plasma, gaming-focused defaults, and hardware/driver paths. Better On should keep the upstream kernel, image update and rollback behavior, and system services. Custom applications should be separately maintained and distributed as Flatpaks when appropriate.

Do not copy a Bazzite interface wholesale. Better On branding, onboarding, catalog, and desktop configuration will be separate, licensed project assets and code. Add image packages only when a requirement cannot be met by the base or Flatpak, and document why each package belongs in the immutable image.

## Component boundaries

| Area | Initial implementation direction |
| --- | --- |
| OS image | `Containerfile` accepts a base image argument, defaulting to `ghcr.io/ublue-os/bazzite:stable`; CI builds desktop AMD/Intel and proprietary NVIDIA variants from their supported Bazzite images. `build_files/build.sh` is the image customization entry point. |
| Desktop and brand | KDE Plasma configuration and original assets under `branding/`; retain upstream Plasma and system settings services. Initial source files include a color scheme and Plasma style seeded for new accounts only when the base profile does not already choose them, a matching wallpaper package, custom launcher icon, and selectable bottom-panel layout template with the Better On menu label. |
| Welcome and Hub | Better On Welcome is a Qt 6 Widgets app built in a Bazzite builder stage and installed for KDE autostart. Its skippable first-run flow introduces the desktop and gaming foundation, opens KDE's Look and Feel settings, and launches Better On Gaming, Discover, and Better On Hub; it persists completion per user. Better On Hub is a separate Qt app with search, categories, a curated catalog, multi-select per-user Flatpak install/update/uninstall, queue progress, pending cancellation, failure reporting, and retries. It validates the fixed Flathub source and signature setting before install/update, updates only apps whose user-scope origin is Flathub, and leaves app data in place on uninstall. It does not invoke a shell. |
| Gaming view | Better On Gaming is a Qt read-only dashboard launched from the application menu. It samples CPU use from `/proc/stat`, reads processor and memory details from `/proc`, reads display-adapter vendor/device/driver data from DRM sysfs, uses `lspci` from `pciutils` for GPU model names, queries root storage with Qt, reports the kernel/product from Qt system information, reads the approximate primary display refresh rate from Qt, finds installed Flatpak gaming launchers using the curated Hub catalog, and scans Steam library manifests for games whose install directories exist. Missing values are labeled unavailable. It does not estimate FPS, temperatures, or game compatibility. |
| Updates and recovery | Bazzite/bootc supported update and rollback flows; Better On can provide understandable status without bypassing them. |
| Installation | A manual VM-image workflow creates a bootable QCOW2 disk from the signed OS digest for QEMU/virt-manager testing. The Anaconda WebUI `bootc-generic-iso` workflow remains available. A separate manual live-ISO workflow assembles pinned Bazzite KDE installer scripts, overlays Better On branding/defaults, and invokes Titanoboa. All artifact workflows target desktop and NVIDIA payloads. None has run or been VM-tested. The live post-install switch retains Bazzite's `--enforce-container-sigpolicy` behavior, backed by a repository-scoped Cosign key and sigstore attachment discovery configuration. |
| CI and distribution | GitHub Actions is configured to build desktop AMD/Intel and proprietary NVIDIA images and publish default-branch images to GHCR under immutable commit tags plus `latest`/`nvidia-latest`. Each image build resolves its selected Bazzite tag to one digest, verifies that digest with the upstream key in `build_files/bazzite-cosign.pub`, and uses that immutable reference for both the native-app build stage and final OS image. The public key at `build_files/cosign.pub` must match the GitHub `SIGNING_SECRET`; CI checks the pair, signs and verifies pushed image digests, and configures the image policy for the project GHCR repository. Cosign uses the legacy registry attachment format that the bootc policy reads. Before constructing either ISO, the workflows pull each tagged image, resolve its registry manifest digest, verify that digest with Cosign, and pass the immutable digest reference into the ISO build. The live workflow applies this to both its shared desktop base and selected install payload. Both workflows upload SHA-256 checksums. These are workflow definitions only until run in a connected repository with registry permissions and the key pair configured. |

## Phases

1. **Foundation (in progress):** establish upstream image recipe, repository structure, brand seed, build/publish CI for AMD/Intel and NVIDIA variants, and manually triggered generic/live installer workflows. Provision the Cosign key pair, then confirm signed image builds and registry publication on Linux CI.
2. **Desktop (early assets started):** create a coherent KDE theme, panel/launcher configuration, wallpaper, and defaults while retaining KDE functionality. Source now includes a Plasma style with Breeze fallback, matching color scheme and wallpaper, branded launcher, and optional panel layout. New-account preferences are merged with the base skeleton without replacing existing values. These assets have not yet been rendered or exercised inside Plasma.
3. **Welcome (initial implementation):** provide a skippable first-login flow for desktop introduction, KDE Look and Feel settings, the gaming dashboard, and optional app browsing/install. Setup completion persists per user. Compile and exercise autostart, each page, skip/back/finish behavior, and the application launch targets in a Plasma VM before marking the phase complete.
4. **Hub (initial implementation):** the catalog includes 23 entries across Browsers, Gaming, Communication, Media & Creativity, Productivity, Utilities, and Development. A live Flathub appstream check confirmed every ID, developer, and icon URL; the Node validation script checks ID uniqueness, metadata, categories, verification labels, and HTTPS listing/icon URLs. The app installs from the user-scoped Flathub remote after checking that the configured source uses HTTPS and signature verification. It can update user-installed catalog apps whose origin is `flathub` and uninstall catalog apps from the user scope without deleting their data. Unverified/listed status, proprietary software, and known Discord sandbox limitations are displayed. Catalog validation passes locally with Node 26.13.1. Compile, inspect Flatpak output parsing against a real system, and exercise install, update, uninstall, cancel, failure, and retry behavior in a Linux/Plasma image before calling this phase complete. Catalog refresh and unified update history remain future work.
5. **Gaming (initial implementation):** the application menu now has Better On Gaming, a real, read-only CPU/GPU/memory/storage/kernel overview with two-second resource refresh, an approximate primary-display refresh rate, catalog-backed detection of installed Flatpak game launchers, and Steam game discovery from common Steam library paths and `appmanifest_*.acf` files. It lists a game only when its manifest and install directory are present. Flatpak is queried without a shell, has a ten-second timeout, and failures are reported in the UI. GPU naming uses `lspci -nn` when available and DRM sysfs fallback details otherwise. Static checks pass, but the app has not compiled or run on Linux. Remaining work includes gaming compatibility details and hardware/driver testing on AMD, Intel, and NVIDIA systems. Do not treat this phase as complete.
6. **Installer (workflows configured, untested):** provide the matching Cosign key pair; build both the Anaconda WebUI ISO and the KDE live ISO; test live boot, the displayed disk identity, storage selection, destructive-action confirmation, installation, first boot, and recovery in a VM. The live ISO workflow overlays Better On branding and defaults on the pinned Bazzite KDE live environment and invokes Titanoboa to compose the ISO. Do not distribute either artifact before these checks.
7. **Quality and release:** validate updates/rollback, accessibility, performance, checksums, and documentation before publishing.

## Current environment and limits

The available host is Windows 10 Home, 64-bit, with about 16 GiB RAM. Git, Bash, CMake, C++ compilers, Flatpak, Podman, QEMU, and GitHub CLI are unavailable. WSL itself is not installed, and the current shell is not elevated; enabling WSL requires administrator access and a Windows restart. This workspace also has no `.git` directory or GitHub remote, so it cannot trigger the configured Actions workflows. The signing public key file `build_files/cosign.pub` is also absent, so the signed VM/ISO workflows cannot pass their signature-verification step yet. Therefore no Qt app, Linux container image, bootable ISO, virtual machine, or OS functionality can be built or tested on this host. The GitHub Actions workflows are the practical build path after the source is connected to a GitHub repository with Actions enabled and signing credentials configured. A successful container build still would not prove ISO boot, installation, hardware support, or rollback.

The base reference follows the public Universal Blue image-template bootc workflow. Desktop/AMD-Intel uses `ghcr.io/ublue-os/bazzite:stable`; proprietary NVIDIA uses `ghcr.io/ublue-os/bazzite-nvidia:stable`, as documented by Bazzite. The generic installer follows the `image-builder` Anaconda WebUI container recipe and pins `ghcr.io/osbuild/image-builder-cli` to a digest. The live installer follows Bazzite revision `264aca11a6bf3dfa2ab68c98315268a65ab9618b` and Titanoboa action revision `5c457c3d0518bd17e754be0fd98a60d29d26abb4`. Both image variants and the exact storage UI still need CI builds and VM tests.

## Phase 1 acceptance

- The base image and build entry point are explicit and small.
- The customization step preserves upstream behavior and adds no persistent services or update overrides. The final image adds `pciutils` for real GPU model reporting in Better On Gaming and `jq` to configure the GHCR-scoped Cosign signature policy while building the image.
- New-account KDE defaults are merged without replacing values already present in the base skeleton; this behavior has a Linux shell regression test in CI.
- CI is configured to publish the default-branch image and build Anaconda WebUI and KDE live ISO artifacts with SHA-256 checksums. The workflows have not run.
- Documentation distinguishes a container image from an installer ISO and states what has not been tested.
- The matching Cosign key pair is configured, Linux CI publishes signed images, both ISO builds and VM installation tests succeed, before Phase 1 is marked complete.

## Phase 3 acceptance

- The image compiles and installs Better On Welcome in a separate build stage.

## Installer safety and scope

- The prior workflow used the legacy `anaconda-iso` type. Upstream documents that type as an unattended installation to the first disk, which did not meet this project's disk-selection safety requirements. The workflow now uses the generic bootc installer flow and a dedicated Anaconda WebUI container.
- The installer recipe sets only the Better On bootc payload in Anaconda's interactive defaults. It has no kickstart storage layout, `autopart`, `clearpart`, or target-disk selection.
- Fedora bug 2332319 reports a bootc install failure involving `/etc/fstab` and `systemd-remount-fs.service`; Fedora marks it fixed in Anaconda 46.6 for Fedora 46. As of 2026-11-22, Fedora 45 is the current release and its stable package is Anaconda 45.30; Fedora 46 remains under development, so switching the installer to Fedora 46 solely to get that fix would mean using a prerelease base. Keep the Fedora 45 installer base until the fix reaches a supported stable base or the documented root-mount workaround has been implemented and VM-validated. See [Fedora bug 2332319](https://bugzilla.redhat.com/show_bug.cgi?id=2332319), [Fedora 45 Anaconda package](https://packages.fedoraproject.org/pkgs/anaconda/anaconda-core/fedora-45.html), and [Fedora release planning](https://fedoraproject.org/wiki/User:Jkurik/Fedora_Release_Life_Cycle).
- This code has not been built on Linux. Until the ISO boots in a VM and a tester confirms the selected drive is clearly identified and destructive writes require confirmation, do not use it on a physical computer or describe it as validated.
- The live ISO workflow targets a Better On-branded KDE session with an installer inherited from the pinned Bazzite/Titanoboa workflow. It has not been built or booted. Published installs depend on the CI-verified Cosign key pair and repository-scoped signature policy.
